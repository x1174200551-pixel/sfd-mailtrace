## 1. 执行原则

1. 先收口最明显的数据权限风险，再做完整 RBAC 和组织架构。
2. 所有数据权限必须以后端为准，前端只做体验层隐藏和提示。
3. 工单、工作台、客户聚合必须使用同一套数据范围口径。
4. 每个任务完成后必须写验收记录，路径为 `docs/验收记录/<任务编号>.md`。
5. 每个阶段通过 Gate 后，才进入下一阶段。

### AUTH-S1 Done 条件

1. AGENT 不能通过列表、详情、附件、客户页看到他人已分配工单数据。
2. AGENT 工作台统计与工单列表口径一致。
3. ADMIN 现有全量功能不回退。
4. 后端全量测试、前端构建、前端 lint 通过。

### AUTH-S2 Done 条件

1. 前端菜单不再依赖 `isAdmin` 硬编码作为唯一来源。
2. 后端管理动作不再只靠 `assertAdmin()`。
3. 旧用户通过 `role_code` 迁移后仍可登录和操作。
4. AUTH-S1 数据范围不回退。
5. 当前版本仍只开放系统内置的管理员、处理人两类角色；后台自建角色不阻塞 AUTH-S2 闭环。

## 10. 风险与控制

| 风险 | 影响 | 控制方式 |
|------|------|----------|
| 数据范围影响统计口径 | 工作台数字和列表数字变化 | S1 必须同步改列表、统计、客户聚合 |
| 权限模型过重 | 拖慢当前业务验收 | 先 S1 快速收口，S2/S3 分阶段 |
| 旧用户迁移失败 | 登录或角色异常 | `role_code` 短期保留兼容回退 |
| 前端隐藏与后端权限不一致 | 页面误显示按钮或接口 403 | 前端按 permissions，后端最终强校验 |
| 自定义角色配置错误 | 新角色可能无菜单或越权 | S2.5 必须保留内置角色保护、权限预览和端到端回归 |
| 部门关系复杂 | TEAM/DEPT 范围难验收 | S3 前确认只用主部门还是多部门 |

## 11. 后续执行要求

1. 后续开发必须按本计划编号推进，不得直接跳到 S2/S3。
2. 每个任务开始前先更新主计划执行游标。
3. 每个任务完成后必须保存验收记录并追加主计划进度记录。
4. 当前 AUTH-S2 先完成管理员、处理人两类系统角色闭环；后台自建角色放到 AUTH-S2.5，整体实施完成后再补充。
5. 若谭总决定不上组织架构，则 AUTH-S3 可标记为 ⏸，但 AUTH-S1、AUTH-S2 和已确认的 AUTH-S2.5 仍建议执行。
