# 邮件回复线程化修复方案

> [!summary] 审核结论
> 实施前自动回复和客服回复本质上都是重新创建一封独立邮件：系统只设置了发件人、收件人、主题和正文，没有发送 `In-Reply-To`、`References`、`Reply-To`，重试时还会生成新的 `Message-ID` 并丢失 HTML 类型。因此本次没有只补两个邮件头，而是同步修复了父消息选择、邮件头生成、发送快照、失败状态、重试一致性和回流匹配。

> [!success] 2026-09-01 实施结果
> V24/V25、线程头构造、固定 Message-ID、发送快照、事务提交后投递、原样重试、原子抢占、未知投递保护、客服回复状态补偿、回复附件 MIME、自动回执、客服回复、客户侧过滤及回复类模板只读主题均已完成；后端全量测试、前端 lint/build 和本地隔离库 V1→V25 迁移通过。当前本机数据库为 MySQL 8.0.46，因此仍需在 MySQL 5.7 测试环境执行迁移与真实邮箱原始 EML 验收，但不得由本地开发过程主动连接或修改远程数据库。

## 1. 目标与边界

### 1.1 目标

1. 自动回执以触发建单的客户来信为父消息，显示在同一邮件会话中。
2. 客服对外回复以当前工单最近一封有效客户来信为父消息，显示在同一邮件会话中。
3. 客户再次回复后，系统能够通过邮件头稳定回流到原工单，不重复建单。
4. 失败重试必须复用首次发送的 `Message-ID`、线程头、主题和正文类型，不得变成另一封新邮件。
5. 前端能够区分发送中、发送成功和发送失败，失败邮件不能伪装成“已成功回复”。
6. 数据库变更兼容 MySQL 5.7，并且只在本地配置和本地数据库验证。
7. 回复附件必须进入最终 SMTP MIME，失败重试从消息附件记录恢复同一组附件。
8. SMTP 调用不得发生在工单业务事务内，避免邮件已发送但业务事务回滚。

### 1.2 本期范围

| 类型 | 是否线程化 | 说明 |
|---|---:|---|
| `AUTO_REPLY` | 是 | 回复触发建单的客户来信 |
| `AGENT_REPLY` | 是 | 回复工单最近一封有效客户来信 |
| `ASSIGN_NOTIFY` | 否 | 内部通知，保持独立邮件 |
| `SLA_WARNING` | 否 | 内部通知，保持独立邮件 |
| `SLA_BREACH` | 否 | 内部通知，保持独立邮件 |
| `TEST` | 否 | 邮箱连通性测试，保持独立邮件 |

### 1.3 非本期范围

- 不对已经投递的历史独立邮件做客户端会话合并；邮件客户端不会因为数据库修复而重排历史邮件。
- 不引入外部消息队列；使用发送日志作为本地投递任务，业务事务提交后再执行 SMTP，并由定时任务补偿遗留任务。
- 不改变分配通知、SLA 通知和飞书群消息的业务范围。
- 不修改远程数据库，不通过 Nacos 注入本次开发配置，不升级 MySQL 5.7。

## 2. 实施前实现核查

### 2.1 已具备的能力

| 能力 | 当前实现 | 结论 |
|---|---|---|
| 收取邮件头 | `IncomingMailParser` 已读取 `Message-ID`、`In-Reply-To`、`References` | 可复用 |
| 来信线程关联 | `MessageThreadService` 先按邮件头、再按主题工单号匹配 | 主流程存在，需增强 |
| 消息表字段 | `mt_ticket_message` 已有 `message_id`、`in_reply_to`、`mail_references` | 无需重复建字段 |
| 邮件去重 | `MessageIdDedupService` 按 `Message-ID` 去重 | 可复用 |
| 邮箱模板选择 | 邮箱可选择自动回执与处理人回复模板 | 正文模板可继续复用 |

### 2.2 已确认的问题

| 编号 | 代码位置 | 问题 | 影响 |
|---|---|---|---|
| R1 | `AutoReplyService.sendAutoReply` | 调用 `sendRawMail`，没有传入触发来信 | 自动回执是新邮件 |
| R2 | `TicketBizService.replyTicket` | 调用 `sendRawMail`，没有选择父消息 | 客服回复是新邮件 |
| R3 | `MailSendService.doSend` | 未设置 `In-Reply-To`、`References`、`Reply-To` | 客户端无法稳定归并会话 |
| R4 | `MailSendService.doRetrySend` | 重新构造邮件并生成新 `Message-ID` | 每次重试可能形成新会话或重复邮件 |
| R5 | `MailSendService.doRetrySend` | 重试统一使用纯文本 | 原 HTML 邮件格式丢失 |
| R6 | `mt_mail_send_log` | 未保存线程头、固定 `Message-ID`、正文类型和关联消息 | 无法原样重试，也无法精确回写消息状态 |
| R7 | `TicketBizService.replyTicket` | 发送前已记录回复事件并改变工单状态，发送失败只写日志 | 页面显示已回复，但客户可能未收到 |
| R8 | `MessageThreadService` | `References` 只取最后一个 ID | 最后一个引用查不到时，不会继续检查祖先消息 |
| R9 | V20 默认模板 | 自动回复和客服回复使用新的业务主题 | 邮件客户端视觉上更像新会话 |
| R10 | `TicketMessageVO` 与前端消息模型 | 没有发送状态 | 页面无法区分待发送、成功和失败 |

## 3. 线程模型

### 3.1 字段约定

| 字段 | 数据库存储 | SMTP 邮件头 |
|---|---|---|
| `message_id` | 去掉尖括号，例如 `abc@example.com` | `<abc@example.com>` |
| `in_reply_to` | 去掉尖括号的单个父消息 ID | `<parent@example.com>` |
| `mail_references` | 规范化后的带尖括号列表 | `<root@example.com> <parent@example.com>` |
| `reply_to_address` | 实际受监控的客服邮箱地址 | `Reply-To: support@example.com` |

所有输入必须拒绝 `\r`、`\n`，防止邮件头注入；消息 ID 必须经过解析、去空、去重和长度校验，不能直接拼接外部邮件头原文。

### 3.2 父消息选择规则

#### 自动回执

直接使用本次刚入库的客户来信作为父消息，调用链显式传递该 `mt_ticket_message.id`。不能再按“最新消息”查询，否则并发拉取或重复任务可能选错父消息。

#### 客服回复

按以下顺序选择：

1. 当前工单中最新一条 `direction = 'INBOUND'` 且 `message_id` 有效的客户来信。
2. 若历史数据没有有效客户来信，则退化为最新一条非 `INTERNAL` 且 `message_id` 有效的消息。
3. 仍找不到时允许独立发送，但必须记录结构化告警和线程降级事件，不能伪造引用头。

客服回复不默认引用最近一封 `OUTBOUND`，避免系统不断回复自己；引用最近客户来信也能让旧工单从下一次回复开始恢复正确会话关系。

查询必须带 `ticket_id`、`is_deleted = 0` 和方向条件：

```sql
SELECT *
FROM mt_ticket_message
WHERE ticket_id = ?
  AND direction = 'INBOUND'
  AND message_id IS NOT NULL
  AND message_id <> ''
  AND is_deleted = 0
ORDER BY id DESC
LIMIT 1;
```

### 3.3 邮件头生成规则

假设父消息为：

```text
Message-ID: parent@example.com
References: <root@example.com> <previous@example.com>
```

新回复生成：

```text
Message-ID: <new-generated-id@sender-domain>
In-Reply-To: <parent@example.com>
References: <root@example.com> <previous@example.com> <parent@example.com>
Reply-To: monitored-mailbox@example.com
```

生成规则：

1. 解析父消息 `mail_references` 中的全部 ID。
2. 按原顺序去重，再追加父消息 `message_id`。
3. 超过 `VARCHAR(1000)` 或邮件头安全长度时，从最旧引用开始裁剪。
4. 必须保留父消息 ID，且父消息 ID 始终位于最后。
5. `Reply-To` 优先使用 `mt_mailbox.email_address`，为空时才退化到 SMTP 用户名。

### 3.4 主题规则

`AUTO_REPLY` 和 `AGENT_REPLY` 的最终主题由系统统一生成：

```text
Re: {原始客户邮件主题}
```

- 已有 `Re:`、`RE:` 或常见本地化回复前缀时不得重复叠加。
- 工单号保留在模板正文和客户查看链接中，不再用新的业务主题破坏会话连续性。
- 通知模板页面中，这两类模板的“邮件主题”改为只读提示“跟随原邮件主题”，客户只维护正文。
- `ASSIGN_NOTIFY`、`SLA_WARNING`、`SLA_BREACH` 等独立通知的主题仍由模板维护。

## 4. 发送模型重构

### 4.1 新增线程化发送请求

保留现有 `sendRawMail` 给独立通知使用，新增线程化请求对象，避免继续扩展长参数列表：

```java
public record OutboundMailRequest(
        Long mailboxId,
        Long ticketId,
        Long ticketMessageId,
        Long templateId,
        String templateType,
        String sendType,
        String toAddress,
        String subject,
        String content,
        String contentType,
        String messageId,
        String inReplyTo,
        String references,
        String replyToAddress
) {}
```

建议增加 `MailThreadHeaders` 值对象，负责消息 ID 规范化、`References` 合并、长度控制和 SMTP 头渲染；业务服务不能自行拼字符串。

### 4.2 固定 Message-ID

1. 发送前生成 RFC 合规的 `Message-ID`，建议格式为 `{UUID}@{发件邮箱域名}`。
2. 在 SMTP 调用前，将完整快照和固定 `Message-ID` 写入 `mt_mail_send_log`。
3. MIME 构造使用可固定 `Message-ID` 的实现，例如覆写 `MimeMessage.updateMessageID()`；调用 `saveChanges()` 时不得替换业务生成的 ID。
4. 首次发送和所有重试都使用同一个 `Message-ID`。

> [!warning] SMTP 不是严格 exactly-once
> 如果 SMTP 服务端已接收邮件，但客户端在收到响应前网络超时，系统仍可能判断失败并重试。固定 `Message-ID` 能帮助服务端和客户端去重，但不能从协议层完全消除重复投递。

### 4.3 发送状态

`mt_ticket_message.send_status` 统一使用：

| 状态 | 含义 | 前端表现 |
|---|---|---|
| `PENDING` | 已创建发送任务，SMTP 尚未确认 | “发送中”弱提示 |
| `SUCCESS` | SMTP 已确认接收 | 正常消息 |
| `FAILED` | 本次发送失败，可从发送日志重试 | 红色“发送失败”并提示管理员处理 |

入站邮件和内部备注直接为 `SUCCESS`。对外回复先建 `PENDING` 消息；只有 SMTP 成功后才能：

- 把消息改为 `SUCCESS`；
- 写入 `sent_at`；
- 更新 `WAITING_CUSTOMER`；
- 写入 `first_reply_at`、`last_agent_reply_at`；
- 记录 `FIRST_REPLY`、`AGENT_REPLY` 成功事件。

发送失败时改为 `FAILED`，保留工单原业务状态，记录发送失败事件，并向前端返回明确失败结果，不能吞掉异常后仍提示回复成功。

发送日志额外使用 `SENDING` 和 `DELIVERY_UNKNOWN`：前者表示执行器已原子抢占，后者表示 SMTP 可能已接收但本地无法确认结果。`DELIVERY_UNKNOWN` 禁止自动重试，只能人工核实，避免重复发信。

### 4.4 事务提交后投递与并发控制

1. 业务事务内只创建 `PENDING` 消息和不可变发送日志，不执行 SMTP。
2. 事务提交后通过同步回调抢占 `PENDING → SENDING`；进程意外退出时，定时任务补偿一分钟前遗留的 `PENDING`。
3. 失败重试使用条件更新抢占 `FAILED → RETRYING`，并在同一条 SQL 中增加 `retry_count`；多实例和手工/定时并发时只有一个执行器能够发送。
4. SMTP 成功后，发送日志和关联消息在独立短事务中一起更新；任一步失败则整个状态事务回滚。
5. `AGENT_REPLY` 成功后按消息行锁幂等更新工单状态、首次响应时间和回复事件；定时任务持续补偿尚未完成的成功回复。

### 4.5 回复附件

客服提交回复时先保存附件元数据并关联 `ticket_message_id`。发送和重试都从该消息读取非内嵌附件，从本地配置的文件存储下载内容，构造 `multipart/mixed`；正文保持原 HTML/纯文本类型，附件文件名使用 UTF-8 并清除换行字符，单封邮件附件原始内容总量限制为 25MB。

### 4.6 重试规则

重试只读取 `mt_mail_send_log` 已保存快照，不重新选择父消息、不重新渲染模板、不重新推断 HTML：

```text
message_id
in_reply_to
mail_references
reply_to_address
subject
content_body
content_type
to_address
```

成功后按 `ticket_message_id` 精确更新原消息为 `SUCCESS`；失败则继续保持 `FAILED` 并增加 `retry_count`。历史发送日志没有新快照字段时，只允许按旧逻辑降级重试并记录告警，不伪造线程关系。

## 5. 数据库变更设计

> [!important] 版本约束
> 当前工作区已经存在 V22、V23，方案预留新迁移为 `V24__mail_reply_thread_headers.sql`。实施前若迁移序号已继续增长，必须使用下一个未占用版本。任何已经执行过的 V1～V23 脚本都不能修改、删除或重命名，避免再次出现 Flyway checksum mismatch。

### 5.1 V24 设计草案

以下 SQL 已落地为 `V24__mail_reply_thread_headers.sql`；语法只使用 MySQL 5.7 支持的 `ALTER TABLE`、`UPDATE` 和普通索引。

```sql
-- mt_mail_send_log：保存首次发送快照，保证重试线程一致
ALTER TABLE `mt_mail_send_log`
  ADD COLUMN `ticket_message_id` BIGINT DEFAULT NULL COMMENT '关联工单消息ID' AFTER `ticket_id`,
  ADD COLUMN `message_id` VARCHAR(255) DEFAULT NULL COMMENT '固定外发Message-ID，不含尖括号' AFTER `content_body`,
  ADD COLUMN `in_reply_to` VARCHAR(255) DEFAULT NULL COMMENT '父消息Message-ID，不含尖括号' AFTER `message_id`,
  ADD COLUMN `mail_references` VARCHAR(1000) DEFAULT NULL COMMENT '规范化References头' AFTER `in_reply_to`,
  ADD COLUMN `reply_to_address` VARCHAR(256) DEFAULT NULL COMMENT '外发Reply-To地址' AFTER `mail_references`,
  ADD COLUMN `content_type` VARCHAR(64) DEFAULT NULL COMMENT '正文MIME类型及字符集' AFTER `reply_to_address`,
  ADD KEY `idx_mt_mail_send_log_message` (`ticket_message_id`),
  ADD KEY `idx_mt_mail_send_log_message_id` (`message_id`);

-- mt_ticket_message：外发消息必须暴露真实发送状态
ALTER TABLE `mt_ticket_message`
  ADD COLUMN `send_status` VARCHAR(16) NOT NULL DEFAULT 'SUCCESS' COMMENT 'PENDING/SUCCESS/FAILED' AFTER `direction`,
  ADD KEY `idx_mt_ticket_message_parent` (`ticket_id`, `direction`, `is_deleted`, `id`);

-- 历史数据只能按现有证据做保守回填
UPDATE `mt_ticket_message`
SET `send_status` = 'FAILED'
WHERE `direction` = 'OUTBOUND'
  AND (`message_id` IS NULL OR `message_id` = '')
  AND `is_deleted` = 0;

UPDATE `mt_ticket_message`
SET `send_status` = 'SUCCESS'
WHERE (`direction` <> 'OUTBOUND' OR (`message_id` IS NOT NULL AND `message_id` <> ''))
  AND `is_deleted` = 0;
```

历史 `OUTBOUND` 且没有 `message_id` 被标记为 `FAILED` 是保守推断，不代表能够证明当时 SMTP 一定失败；上线前应输出数量并人工抽样。

### 5.2 V25 投递一致性

V25 为 `mt_ticket_message` 增加 `delivery_completed_at` 和补偿扫描索引。该字段是客服回复成功后工单状态与事件已经完成更新的幂等标记；历史成功外发使用已有时间回填，避免升级后重复生成事件。迁移仅使用 MySQL 5.7 支持的普通列、索引、`COALESCE` 和 `UPDATE`。

### 5.3 实体与接口同步

| 层级 | 变更 |
|---|---|
| `MailSendLogEntity` | 增加发送快照字段 |
| `TicketMessageEntity` | 增加 `sendStatus` |
| `TicketMessageVO` | 返回 `sendStatus` |
| 前端 `TicketMessage` | 增加 `sendStatus` 联合类型 |
| 工单详情接口 | 不新增端点，只扩展消息字段 |

## 6. 业务流程

### 6.1 自动回执

```text
IMAP 拉取并解析客户邮件
  → 入站消息落库（保留 Message-ID / References）
  → 显式传入该入站消息 ID
  → 构造线程头和 Re: 原主题
  → 创建 OUTBOUND/PENDING 消息
  → 创建发送日志及不可变快照
  → SMTP 发送
     ├─ 成功：消息 SUCCESS + 自动回复成功事件
     └─ 失败：消息 FAILED + 失败事件，工单创建不回滚
```

### 6.2 客服回复

```text
权限与数据范围校验
  → 查询当前工单最近有效 INBOUND 父消息
  → 渲染正文，主题跟随原邮件
  → 创建 OUTBOUND/PENDING 消息及附件关联
  → 创建发送日志及不可变快照
  → SMTP 发送
     ├─ 成功：消息 SUCCESS → 更新响应时间/工单状态/成功事件
     └─ 失败：消息 FAILED → 保持原工单状态 → 返回明确失败
```

### 6.3 失败重试

```text
读取失败发送日志
  → 校验邮箱仍可用
  → 原样恢复首次发送 MIME 快照
  → 复用同一 Message-ID 和线程头
  → SMTP 发送
     ├─ 成功：日志 SUCCESS + 精确更新原消息 SUCCESS
     └─ 失败：日志 FAILED + retry_count + 1
```

### 6.4 客户回信

```text
读取 In-Reply-To
  → 未命中则按 References 从新到旧逐个匹配
  → 未命中再尝试主题工单号
  → 均未命中才新建工单
```

所有消息 ID 匹配继续受企业边界限制，不能只凭全局 `Message-ID` 跨企业关联工单。

## 11. 风险与监控

| 风险 | 控制方式 |
|---|---|
| SMTP 接收成功但客户端超时 | 固定 Message-ID；监控同 ID 重试；接受 SMTP 非 exactly-once 的协议边界 |
| 历史消息没有 Message-ID | 最近有效入站降级；无父消息时独立发送并告警 |
| References 过长 | 从最旧引用裁剪，始终保留直接父消息 |
| 恶意邮件头注入 | 拒绝 CR/LF，只接受解析后的 Message-ID token |
| 发送成功但业务事务回滚 | 业务事务提交后才执行 SMTP；遗留 `PENDING` 由定时任务补偿 |
| SMTP 结果无法确认 | 标记 `DELIVERY_UNKNOWN` 并停止自动重试，要求人工核实 |
| 多执行器重复重试 | 条件更新原子抢占，同一发送日志只有一个执行器进入 SMTP |
| 历史无 Message-ID 外发误判失败 | 上线前统计与抽样；保留人工修正 SQL |
| 旧日志无法原样重试 | 仅旧日志允许降级，所有新日志强制保存完整快照 |

建议新增指标：

- `mail_send_threaded_total{type,status}`：线程邮件发送量。
- `mail_send_thread_fallback_total{reason}`：无父消息等降级次数。
- `mail_send_retry_total{result}`：重试次数与结果。
- `mail_thread_match_total{source}`：按 `in_reply_to`、`references`、`ticket_no` 的回流命中量。
- `mail_thread_new_ticket_after_reply_total`：疑似回信错误新建工单数量。
