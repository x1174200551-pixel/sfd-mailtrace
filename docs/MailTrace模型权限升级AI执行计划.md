目标：在现有 MailTrace 工单、邮箱、SLA、分配规则、自动回复模板、用户、角色、组织能力基础上，升级为“企业业务归属 + 邮箱策略入口 + 用户企业/邮箱授权”的权限模型，并完成对应前端调整。

## 0. 已确认开发基线（2026-08-26）

以下结论已经确认，后续 AI 不得重复假设或改回旧口径：

1. 在当前分支 `权限重构` 开发，不新建其他开发分支。
2. Flyway 迁移号必须读取仓库当前最大版本后顺延，禁止复用已经存在的版本号。当前最大版本为 `V17__customer_ticket_access_and_random_number.sql`，因此本次企业权限模型迁移使用 `V18__enterprise_mailbox_permission_model.sql`；如果开发前又新增迁移，则继续顺延。
3. 数据库迁移必须兼容 MySQL 5.7；本地允许使用 MySQL 8.0 验证，但 SQL 不得使用 MySQL 8 专属语法。
4. 本地后端端口统一为 `8080`，前端本地代理也统一指向 `http://127.0.0.1:8080`。
5. 本期用户保持单角色、单部门：用户只保存一个 `roleCode` 和一个 `departmentId`，不实现多角色、多部门和主部门切换。
6. 本地开发使用 `application.yml` 和本地 MySQL，`NACOS_CONFIG_ENABLED=false`；不得使用指向外部数据库的 `application-test.yml` 作为开发配置。
7. 权限切换采用“先扩表回填、再影子验证、最后一次性切权”：新增表和回填期间旧角色数据范围继续生效；没有完成新权限全链路验证前，不得停止旧权限读取。
8. 可读范围和可操作范围分开：历史查询可读取已授权的未删除邮箱数据；新建、收信、分配、策略选择只允许启用企业和启用邮箱。

## 1. 复核结论

### 1.1 文档方向可采用

两份 Obsidian 文档的核心方向和当前系统演进目标一致：

1. 企业作为业务数据归属边界，不做物理多租户。
2. 邮箱归属企业，并作为自动回复模板、SLA、分配规则组的策略绑定入口。
3. 部门和处理人继续作为全局运营组织，不挂企业。
4. 角色只控制菜单、按钮、接口能力，不再控制业务数据范围。
5. 业务数据权限统一收口为“历史可读邮箱 + 业务可操作邮箱”。
6. 工单创建时固化企业、邮箱、模板、SLA、规则组、命中规则等快照字段。

### 1.2 当前代码尚未落地的关键差异

当前仓库仍是旧权限模型，可以先做不改变现有行为的企业字段扩展和历史回填，但不能直接停用旧范围或切换部分业务查询：

| 领域 | 当前代码现状 | 对新模型的影响 |
|---|---|---|
| 角色数据范围 | `mt_role_data_scope` 已建表，`PermissionService` 仍读取 `dataScopes`，登录和角色接口仍返回/保存 `dataScopes` | P0-EXPAND 期间继续生效；P2-CUTOVER 与全部业务查询一起原子退场 |
| 工单数据权限 | `DataScopeService` 当前按角色 `ALL/SELF/DEPT/DEPT_AND_CHILDREN` 和 `assignee_id` 过滤 | 需要改为按 `mailbox_id in visibleMailboxIds` 过滤 |
| 邮箱模型 | `mt_mailbox` 只有 `auto_reply_template_id`，无 `enterprise_id/sla_policy_id/assignment_rule_group_id/assignment_fallback_type` | 邮箱尚不能作为完整策略入口 |
| 自动回复 | `AutoReplyService` 仍按全局 `template_code=AUTO_REPLY` 查模板 | 需要改为优先读取邮箱绑定模板 |
| SLA | `SlaDeadlineService` 仍按启用默认策略选择 | 需要改为按邮箱绑定策略计算，未绑定不计算 |
| 分配规则 | `AssignmentRuleService` 仍是全局规则池，`DEFAULT` 仍生效 | 需要新增规则组，并让规则只通过邮箱绑定规则组生效 |
| 前端角色页 | `RoleManagePage` 仍展示和提交“默认数据范围” | 必须删除该区块和提交字段 |
| 前端用户页 | `UserManagePage` 仅维护账号、角色、部门、状态 | 必须增加可见企业/可见邮箱授权维护 |
| 前端邮箱页 | `MailboxManagePage` 没有企业、SLA、规则组、fallback 配置 | 必须改造为策略配置入口 |

### 1.3 计划修正

原文档中的阶段顺序调整为安全切换模型：

1. `G0` 文档确认、本地配置对齐和基线冻结。
2. `P0-EXPAND` 数据库扩展、历史数据回填；旧角色数据范围继续生效。
3. `P1-SHADOW` 用户企业/邮箱权限核心和影子验证；不改变线上查询结果。
4. `P2-CUTOVER` 一次性完成业务查询切权、旧角色数据范围退场和后端兼容。
5. `P3` 企业、邮箱、模板、SLA、规则组配置接口。
6. `P4` 建单、自动回复、SLA、自动分配核心链路。
7. `P5` 前端页面、菜单、用户授权和角色页调整。
8. `P6` 联调、迁移演练和上线门禁。

## 2. 总准入门禁

后续每个 AI 执行任务开始前都必须满足以下条件：

1. 读取本计划、两份 Obsidian 源文档、当前 `git status --short`。
2. 不回滚与当前任务无关的既有改动。
3. 新增数据库迁移必须先读取 `backend/src/main/resources/db/migration` 当前最大版本后追加；当前最大版本为 V17，本次使用 `V18__enterprise_mailbox_permission_model.sql`，如基线变化继续顺延。
4. Flyway 脚本必须兼容 MySQL 5.7，避免 MySQL 8 专属语法。
5. 每个阶段只修改本阶段文件；`P2-CUTOVER` 是不可拆分的权限切换单元，禁止只切部分业务查询或只停止旧权限读取。
6. 后端接口权限使用 `@RequirePermission` 或当前控制器既有权限校验方式，不能只靠前端隐藏。
7. 历史查询必须先套“可读邮箱”权限，新收信、建单、配置选择、分配和转派必须使用“可操作邮箱”，再叠加企业、邮箱、我的、本部门、待分配等业务筛选。
8. 管理员可读全部未删除邮箱、只可操作启用企业下的启用邮箱；普通用户无授权时业务数据返回空集合，不回退到角色范围。
9. 每阶段完成后必须产出验收记录，包含改动文件、接口变更、测试命令、通过/失败结论、遗留问题。
10. 用户模型固定为单角色、单部门，接口和页面均使用单值字段，不新增 `roleCodes`、`departmentIds`、`primaryDepartmentId`。
11. 本地启动端口固定为 8080，前后端代理必须一致；本地开发关闭 Nacos 并连接本地数据库。
12. 本地验收数据至少包含两个企业、三个邮箱、管理员、企业授权用户、单邮箱授权用户、空授权用户。

业务确认门禁：

| 编号 | 待确认项 | 当前建议 |
|---|---|---|
| BIZ-01 | 菜单是否把“通知模板”改名为“自动回复模板” | 建议保留“通知模板”，页面内用模板类型筛选，避免后续分配通知、SLA 提醒无菜单归属 |
| BIZ-02 | 企业停用是否强制停用企业下邮箱 | 第一阶段不强制，只禁止新收信/新建单，页面展示风险 |
| BIZ-03 | 邮箱未绑定自动回复模板时是否发送 | 第一阶段不发送，记录配置缺失事件 |
| BIZ-04 | 邮箱未绑定 SLA 时是否计算 | 不计算，页面展示“未配置 SLA” |
| BIZ-05 | 非管理员用户是否必须至少一个授权 | 新建/编辑时建议强制，否则会出现空数据账号 |
| BIZ-06 | 企业授权是否包含未来新增邮箱 | 建议包含，并在用户授权区提示 |

### P1-SHADOW：用户企业/邮箱权限核心和影子验证

目标：建立新的邮箱授权解析和断言服务，通过影子计算验证结果，但暂不替换旧 `DataScopeService` 的生产查询条件。

准入门禁：

1. `P0-EXPAND` 完成。
2. 历史用户授权已回填并完成抽样。
3. 可读邮箱与可操作邮箱算法已确认。

后端实施动作：

1. 新增 `EnterpriseMailboxAccessService`，本阶段不改旧 `DataScopeService` 的生产行为。
2. 实现 `isAdmin(principal)`；本期单角色，统一依据当前有效角色编码判断，不依赖数据授权。
3. 实现 `resolveVisibleEnterpriseIds(principal)`。
4. 实现 `resolveReadableMailboxIds(principal)`：用于历史工单、客户、日志、附件和原始 EML 查询，包含已授权且未删除的停用邮箱。
5. 实现 `resolveOperationalMailboxIds(principal)`：用于新收信、建单、策略选择、分配和转派，只包含启用企业下的启用邮箱。
6. 实现 `assertMailboxReadable`、`assertMailboxOperational`、`assertEnterpriseVisible`、`assertAssigneeCanAccessMailbox`。
7. 普通用户空授权必须返回空集合；禁止用空 `in` 跳过条件后查全表。
8. 加请求级缓存，避免一个请求多次解析同一用户授权。
9. 增加影子对照：在不影响响应的前提下比较旧角色范围和新邮箱范围，仅记录用户 ID、范围数量和差异数量，不记录业务敏感内容。
10. 更新单元测试覆盖管理员、企业授权、邮箱授权、并集、空授权、停用授权、停用邮箱和历史可读场景。

输出：

1. 新权限服务和影子对照结果。
2. 单元测试。
3. 验收记录：`docs/验收记录/MODEL-P1-SHADOW.md`。

验收标准：

1. 管理员历史查询可读全部未删除邮箱，业务操作只使用启用邮箱。
2. 普通用户企业授权可读该企业未删除邮箱，业务操作只使用其中启用邮箱。
3. 普通用户邮箱授权只可见指定邮箱。
4. 企业授权和邮箱授权取并集。
5. 普通用户空授权不能看到业务数据。
6. `assertAssigneeCanAccessMailbox` 能拦截跨邮箱错误分配。
7. 生产查询仍由旧角色数据范围控制，影子阶段不改变用户实际结果。

回滚：

1. 若新权限服务异常，关闭影子计算或回滚本阶段代码即可。
2. 旧角色数据范围仍在生效，无权限切换回滚压力。

### P2-CUTOVER：业务权限一次性切换和角色数据范围退场

目标：在一个不可拆分的发布单元中，把所有业务数据查询切换到用户邮箱授权，同时停止角色数据范围读写；禁止只完成其中一部分。

准入门禁：

1. `P1-SHADOW` 完成，影子差异已解释并通过验收。
2. 本地验收账号和两企业三邮箱数据已准备完成。
3. 工单、客户、工作台、收发日志、邮箱、附件、原始 EML 的权限入口清单已逐项确认。

后端实施动作：

1. 工单列表、统计、详情、回复、备注、领取、转派、附件、原始 EML 全部使用可读/可操作邮箱断言。
2. 客户列表、详情和聚合只统计当前可读邮箱关联工单，禁止暴露企业内其他邮箱的工单数量。
3. 工作台、收件记录、发件记录和邮箱列表统一追加当前用户邮箱范围。
4. “全部、我的、本部门、待分配”只作为可读邮箱范围内的视图筛选。
5. 默认处理人、规则处理人和手动转派候选必须是启用用户、具备工单处理权限，并可操作目标邮箱。
6. 修改 `PermissionService`，停止解析 `mt_role_data_scope`；`PermissionContext.dataScopes` 短期返回空对象兼容旧前端。
7. 修改 `RoleManagementService`，角色权限保存只写 `mt_role_permission`；请求中的旧 `dataScopes` 字段短期兼容忽略，不再写表。
8. `mt_role_data_scope` 表和历史数据保留，不删除。
9. 完成所有数据权限单元测试和接口越权测试后，才允许合并本切换单元。

输出：

1. 全业务查询权限切换。
2. 角色数据范围运行链路退场。
3. 验收记录：`docs/验收记录/MODEL-P2-CUTOVER.md`。

验收标准：

1. 普通用户不能通过列表参数、详情 ID、附件 ID、消息 ID 绕过邮箱授权。
2. 空授权用户所有业务数据接口返回空集合或 403，不得查全表。
3. 工作台、客户和日志统计与同条件工单列表一致。
4. 管理员可以查看停用邮箱历史数据，但不能把停用邮箱用于新业务操作。
5. 后端全量测试通过，权限越权矩阵通过。

回滚：

## 5. 审核结论

### 5.1 可执行性审核

结论：可以执行，但必须按 `G0 -> P0-EXPAND -> P1-SHADOW -> P2-CUTOVER -> P3 -> P4 -> P5 -> P6` 顺序推进。

理由：

1. 先扩表、回填且保持旧权限生效，避免数据库升级本身改变用户可见结果。
2. 新邮箱授权先影子计算并解释差异，再将全部业务查询和旧角色范围退场放进同一个切换单元，避免双权限或半切换。
3. 企业字段、邮箱策略字段、规则组字段依赖数据库迁移，不能由前端先行假接。
4. 建单链路涉及自动回复、SLA、分配规则、客户、日志，必须在配置接口之后改。
5. 前端页面依赖后端接口和 VO 稳定后再改，能减少返工。

### 5.2 风险审核

| 风险 | 等级 | 处理 |
|---|---|---|
| 角色数据范围和用户授权并存 | 高 | `P1-SHADOW` 只比较不改响应；`P2-CUTOVER` 一次性停止旧范围读写 |
| 历史普通用户上线后无数据 | 高 | `P0-EXPAND` 初始化默认企业授权，上线前抽样核对 |
| 只切换部分业务查询导致越权 | 高 | `P2-CUTOVER` 作为不可拆分发布单元，按入口清单做越权测试 |
| 空授权查询误查全表 | 高 | `P1-SHADOW/P2-CUTOVER` 空集合必须显式转为无结果条件 |
| 邮箱跨企业绑定模板/SLA/规则组 | 高 | `P3` 保存时强校验企业一致 |
| 处理人被分配到不可见邮箱工单 | 高 | `P2-CUTOVER/P4` 统一使用 `assertAssigneeCanAccessMailbox` |
| SLA 默认策略继续误作用 | 中 | `P4` 建单只按邮箱绑定策略计算 |
| DEFAULT 分配规则继续误命中 | 中 | `P4` 规则组模型不再执行全局 DEFAULT |
| 前端隐藏但接口未拦截 | 高 | 后端每个接口和下载都做权限校验 |
| MySQL 5.7 兼容问题 | 中 | 当前最大版本顺延的迁移不得使用 8.0 专属语法，先在 5.7 兼容环境演练 |

### 5.3 范围审核

本计划不包含：

1. 复杂 CRM 客户体系。
2. 企业自己的部门树或企业服务团队表。
3. 物理多租户隔离。
4. 企业级编号规则。
5. 邮箱组、处理人组、批量授权高级能力。
6. 删除 `mt_role_data_scope` 表的清理任务。

这些能力可以在新模型稳定后单独立项。

### 5.4 最终审核意见

采用“企业业务归属 + 全局运营组织 + 用户企业/邮箱授权”的轻量模型是当前阶段最稳妥的方案。技术基线已确认；下一步先执行 `G0` 关闭剩余业务门禁，再从 `P0-EXPAND` 开始。禁止先停用旧角色范围，也禁止绕过影子验证直接做权限切换。
