# 权限体系与数据权限落地优化方案

| 字段 | 内容 |
|------|------|
| 文档状态 | 已拆执行计划；AUTH-S1 已开始执行 |
| 编写时间 | 2026-07-28 |
| 适用范围 | MailTrace 邮件工单系统 |
| 当前目标 | 设计组织架构、RBAC、数据权限的可落地方案；暂不纳入指定邮箱和客户标签数据范围 |
| 对应执行计划 | `docs/权限体系与数据权限阶段执行计划.md` |

## 1. 背景与现状

当前系统已经完成第一版功能权限雏形，但权限模型仍偏轻：

1. 用户表只有 `role_code`，当前固定为 `ADMIN` / `AGENT`。
2. 前端菜单通过 `user.roleCode === 'ADMIN'` 控制管理菜单显示。
3. 后端 Service 主要使用 `assertAdmin()`、`assertAgentOrAdmin()` 进行硬编码判断。
4. 工单列表、详情、工作台统计、客户聚合尚未统一套数据范围。
5. 非管理员虽然只能看到工作空间和工单中心，但仍可能看到所有工单和客户数据。

因此当前问题不是“菜单权限没做”，而是“数据权限没有收口”。后续要把菜单权限、操作权限、数据范围拆开设计，避免只靠前端隐藏。

## 2. 设计边界

### 2.1 本方案包含

| 模块 | 目标 |
|------|------|
| 组织架构 | 支持部门、团队、上下级或负责人关系 |
| RBAC | 支持角色、菜单权限、操作权限 |
| 数据权限 | 支持全部、本人、团队、部门、部门及下级 |
| 工单落地 | 工单列表、详情、操作、工作台、客户聚合统一应用数据范围 |

### 2.2 本方案暂不包含

| 范围 | 说明 |
|------|------|
| 指定邮箱 `MAILBOX` | 暂不做邮箱级数据授权，避免和邮箱管理、分配规则复杂耦合 |
| 客户标签 `CUSTOMER_TAG` | 当前客户模块仍是只读聚合，客户标签体系尚未建立 |
| 复杂外部组织同步 | 第一阶段先按本系统内置组织模型设计，后续再接企业组织架构 |
| 细粒度字段脱敏 | 如客户邮箱部分脱敏、内部备注可见性，后续可作为安全增强项 |

## 3. 权限模型拆分

权限体系拆成三层，不混在一个角色字段里。

| 层级 | 解决问题 | 示例 |
|------|----------|------|
| 组织架构 | 用户属于哪里、谁管谁 | 部门、团队、主管 |
| RBAC | 用户能进入什么页面、能做什么动作 | 菜单、按钮、接口动作 |
| 数据权限 | 用户能看哪些业务数据 | 全部、本人、团队、部门、部门及下级 |

组织架构只提供关系，RBAC 只判断功能，数据权限负责过滤业务数据。三层独立后，后续扩展主管、团队、部门权限会更稳。

## 4. 目标角色建议

第一阶段可以先保留当前 `ADMIN` / `AGENT`，新增主管角色可作为第二阶段。

| 角色 | 说明 | 菜单权限 | 默认数据范围 |
|------|------|----------|--------------|
| `ADMIN` 管理员 | 系统管理员 | 全部菜单 | `ALL` |
| `AGENT` 客服处理人 | 一线客服 | 工作台、全部工单、客户只读 | `SELF` + 未分配池 |
| `SUPERVISOR` 客服主管 | 后续扩展 | 工作台、全部工单、客户只读、部分管理视图 | `TEAM` 或 `DEPT` |

说明：如果本期不想新增主管角色，可以先在 RBAC 表结构里预留，实际只迁移 `ADMIN` 和 `AGENT`。

## 5. 数据范围定义

本方案暂定以下数据范围：

| 范围 | 编码 | 含义 |
|------|------|------|
| 全部 | `ALL` | 可查看全部业务数据 |
| 本人 | `SELF` | 只看自己负责或自己参与的数据 |
| 团队 | `TEAM` | 看所在团队成员负责的数据 |
| 本部门 | `DEPT` | 看所属部门成员负责的数据 |
| 本部门及下级 | `DEPT_AND_CHILDREN` | 看所属部门及下级部门成员负责的数据 |

### 5.1 未分配池规则

未分配工单是特殊公共池，建议默认可见：

| 角色 | 是否可见未分配工单 | 说明 |
|------|--------------------|------|
| `ADMIN` | 是 | 管理员可统一调度 |
| `AGENT` | 是 | 处理人可以领取待分配工单 |
| `SUPERVISOR` | 是 | 主管可看本团队或全局未分配，具体口径待定 |

建议第一阶段口径：`AGENT = assignee_id = 当前用户 OR assignee_id IS NULL`。

### 6.3 数据权限

#### `mt_role_data_scope`

| 字段 | 说明 |
|------|------|
| `role_id` | 角色 ID |
| `biz_type` | 业务类型，如 `TICKET`、`CUSTOMER`、`DASHBOARD` |
| `scope_type` | `ALL` / `SELF` / `TEAM` / `DEPT` / `DEPT_AND_CHILDREN` |

#### `mt_user_data_scope_override`

可选表，用于个别用户覆盖默认角色范围。

| 字段 | 说明 |
|------|------|
| `user_id` | 用户 ID |
| `biz_type` | 业务类型 |
| `scope_type` | 覆盖数据范围 |
| `enabled` | 是否启用 |

第一版可以不做 override，只做角色默认数据范围。

## 8. 后端落地方式

### 8.1 当前硬编码权限逐步替换

当前常见判断：

```java
assertAdmin(principal);
assertAgentOrAdmin(principal);
```

建议逐步替换为：

```java
permissionService.require(principal, "ticket:view");
permissionService.require(principal, "assignment-rule:manage");
```

### 8.2 统一数据范围服务

新增 `DataScopeService`，负责根据用户和业务类型生成查询范围。

建议接口：

```java
DataScope resolve(CurrentUserPrincipal principal, String bizType);
void applyTicketScope(LambdaQueryWrapper<TicketEntity> wrapper, CurrentUserPrincipal principal);
void assertTicketVisible(CurrentUserPrincipal principal, TicketEntity ticket);
void assertTicketOperable(CurrentUserPrincipal principal, TicketEntity ticket, String actionCode);
```

### 8.3 工单必须套数据范围的位置

| 位置 | 当前风险 | 优化 |
|------|----------|------|
| 工单列表 `pageTickets` | `AGENT` 可查全部 | 查询 wrapper 套数据范围 |
| 工单详情 `getTicket` | 只校验角色 | 详情返回前校验可见 |
| 回复/备注/关闭/状态/优先级 | 只校验角色 | 操作前校验可操作 |
| 转派 | 普通处理人可转派范围不清 | 区分 `ticket:assign` 和 `ticket:claim` |
| 附件下载 | 可能绕过详情权限 | 下载前校验工单可见 |
| 工作台统计 | 当前偏全量 | 按数据范围统计 |
| 客户聚合 | 客户邮箱可能全量暴露 | 只聚合当前可见工单对应客户 |
| SLA 超时统计 | 当前偏全量 | 按数据范围统计 |
| 导出 | 后续如启用必须过滤 | 导出复用列表数据范围 |

### 8.4 第一阶段建议查询规则

#### `ADMIN`

```sql
WHERE is_deleted = 0
```

#### `AGENT`

```sql
WHERE is_deleted = 0
  AND (
    assignee_id = :currentUserId
    OR assignee_id IS NULL
  )
```

#### `SUPERVISOR`

```sql
WHERE is_deleted = 0
  AND (
    assignee_id IN (:teamMemberIds)
    OR assignee_id IS NULL
  )
```

如果使用部门范围，则 `teamMemberIds` 替换为部门成员 ID 集合。

## 9. 前端落地方式

### 9.1 登录态返回权限清单

`/auth/login` 和 `/auth/me` 建议返回：

```json
{
  "user": {
    "id": 2,
    "account": "agent01",
    "displayName": "客服一号"
  },
  "roles": ["AGENT"],
  "permissions": [
    "menu:workspace.dashboard",
    "menu:ticket.all",
    "ticket:view",
    "ticket:reply"
  ],
  "dataScopes": {
    "TICKET": "SELF",
    "CUSTOMER": "SELF",
    "DASHBOARD": "SELF"
  }
}
```

### 9.2 菜单显示

前端不再写死 `isAdmin` 控制菜单，改为按权限编码判断：

```ts
can("menu:sla.policy")
can("menu:system.user")
```

### 9.3 按钮显示

工单详情按钮按权限和当前工单可操作状态显示：

| 按钮 | 显示条件 |
|------|----------|
| 回复客户 | `ticket:reply` 且后端认为可操作 |
| 内部备注 | `ticket:note` 且工单可见 |
| 转派 | `ticket:assign` |
| 领取 | `ticket:claim` 且未分配 |
| 关闭 | `ticket:close` 且工单非终态 |
| 修改优先级 | `ticket:update-priority` |

前端只做体验控制，最终以后端校验为准。

## 10. 业务口径建议

### 10.1 普通处理人

| 页面/动作 | 建议 |
|-----------|------|
| 工作台 | 只看自己负责 + 未分配池统计 |
| 全部工单 | 默认只返回自己负责 + 未分配 |
| 工单详情 | 只能打开自己可见范围内工单 |
| 客户管理 | 只聚合自己可见工单对应客户 |
| 回复/备注 | 只能操作自己负责的工单 |
| 未分配工单 | 可领取，领取后成为负责人 |
| 转派 | 第一阶段可不开放，或只允许转出自己负责的工单 |

### 10.2 主管

| 页面/动作 | 建议 |
|-----------|------|
| 工作台 | 看团队或部门统计 |
| 全部工单 | 看团队或部门成员工单 |
| 转派 | 可在团队内转派 |
| 客户管理 | 聚合团队可见工单对应客户 |

### 10.3 管理员

管理员拥有全部菜单、全部动作、全部数据范围。

## 11. 兼容与迁移策略

### 11.1 不破坏当前用户

迁移时保留 `mt_user.role_code`，短期内作为兼容字段。

建议迁移步骤：

1. 新增 RBAC 和组织表。
2. 初始化系统角色 `ADMIN` / `AGENT`。
3. 根据 `mt_user.role_code` 回填 `mt_user_role`。
4. 登录时优先读取 `mt_user_role`，如果没有角色关系再回退 `role_code`。
5. 稳定后再决定是否保留或废弃 `role_code`。

### 11.2 默认权限初始化

| 角色 | 初始化权限 |
|------|------------|
| `ADMIN` | 全部菜单、全部动作、`ALL` 数据范围 |
| `AGENT` | 工作台、全部工单、客户只读、工单查看、回复、备注、领取、关闭自己工单，`SELF` 数据范围 |
| `SUPERVISOR` | 第二阶段再启用 |

## 12. 验收标准

### 12.1 菜单权限

1. 管理员可见全部已实现菜单。
2. 处理人只可见工作台、全部工单、客户管理。
3. 直达无权限页面或接口返回 403，不暴露管理数据。

### 12.2 数据权限

1. 管理员工单列表返回全部工单。
2. 处理人工单列表只返回自己负责 + 未分配。
3. 处理人无法通过 ID 访问不可见工单详情。
4. 处理人无法回复、关闭、转派不可见或不可操作工单。
5. 工作台统计与全部工单列表口径一致。
6. 客户管理只聚合当前用户可见工单对应客户。
7. 附件下载、导出、SLA 统计均不能绕过数据范围。

### 12.3 回归

1. 现有管理员功能不回退。
2. G3/G4 工单主闭环不受影响。
3. 分配规则、SLA 策略、工作日历等管理功能仍仅管理员可维护。
4. 登录、刷新、token 解析兼容旧用户。

## 13. 待确认问题

| 编号 | 问题 | 建议默认值 |
|------|------|------------|
| Q1 | 普通处理人是否可见未分配工单 | 可见 |
| Q2 | 普通处理人是否可以领取未分配工单 | 可以 |
| Q3 | 普通处理人是否可以转派自己的工单 | 第一阶段先不开放，或仅允许转给管理员/主管指定范围 |
| Q4 | 主管角色是否本期纳入 | 先预留，第二阶段启用 |
| Q5 | 团队和部门是否都要做 | 第一阶段只做部门即可；团队可由部门承担 |
| Q6 | 一个用户是否允许多个部门 | 表结构支持，第一阶段只使用主部门 |
| Q7 | 客户页是否对处理人开放 | 开放，但只聚合其可见工单客户 |

## 14. 推荐结论

建议后续按“先数据权限收口，再 RBAC 配置化，再组织架构增强”的方式推进：

1. 先修复最明显的数据泄露风险：`AGENT` 不再看全量工单和客户。
2. 再把前后端硬编码角色判断迁移到权限码。
3. 最后接入组织架构和主管视角。

本方案只定义落地口径，暂不拆阶段执行计划。待谭总审阅确认后，再按计划文件规范拆分阶段任务、验收标准和执行游标。
